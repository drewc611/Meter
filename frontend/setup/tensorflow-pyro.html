TensorFlow / Pyro setup

There's no dedicated TensorFlow or Pyro integration shipping today — Merit's built-in reference proxies target hosted LLM APIs (see Python). What follows is the honest pattern for reporting spend from a custom model-training or probabilistic-modeling pipeline, using the same generic /ingest/usage contract.

The schema doesn't care what "usage" means

source_system and tool are plain strings, not a fixed enum — UsageEvent only needs an amount, attributed to a person, tagged with something identifying. That's enough to report a training run's compute cost the same way a hosted-API call gets reported. 

# at the end of a training run, once you know the real GPU-hour cost
requests.post(f"{MERIT_API_BASE}/ingest/usage", json={
    "source_system": "internal_training",
    "external_id": external_id_for(researcher_email),
    "tool": "tensorflow",          # or "pyro", or "tensorflow+pyro" if it's a hybrid run
    "model": run_config.model_name,
    "cost_usd": round(gpu_hours * hourly_rate, 6),
}, headers={"Authorization": f"Bearer {MERIT_INGEST_TOKEN}"})

Where gpu_hours * hourly_rate is whatever your actual cloud or on-prem accounting gives you for that job — Merit doesn't compute compute cost itself, it just needs the number and who to attribute it to.

What "value" and "slop" mean in this context

Outcome and quality signals still have to come from somewhere real — Merit doesn't infer whether a training run was worthwhile. If your team tracks experiment outcomes (a model that shipped vs. one that was scrapped, a Pyro inference that got trusted vs. one that was thrown out), those map to POST /ingest/outcome and POST /ingest/quality-signal the same way a GitHub PR merge or revert does for code — see Architecture.

If you want this built in properly

This page describes a pattern you can wire up today, not a maintained connector. If a real TensorFlow/Pyro integration would be useful, that's a product conversation, not something to assume from this guide alone.
